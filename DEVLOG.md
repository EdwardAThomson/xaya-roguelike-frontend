# Development Log

## 2026-09-18

A day of playing the game rather than reading it, which turned up a pile of co-op and duel breakage that 275 backend tests and 23 parity vectors had all been blind to, since none of it lives in the engine. The worst were the ones that made a run unplayable. A duel salt was held only in memory, so reloading a tab after committing a round left the reveal impossible to reconstruct and deadlocked both players until the void timeout; sealed choices are now persisted per visit and per round and cleared when the run ends. A solo run sets `active_visit` exactly as a co-op one does, and three places read that as "you are in a co-op visit", so the Co-op tab described a solo run as waiting for a partner and offered to cancel it, while `doCoopHost` and `doCoopJoin` refused outright a few lines above the code that builds the exit settlement for that very case, meaning the documented "host from inside a run" flow had never once worked. Leaving a run had no control at all: the `coop-exit` handler existed but nothing rendered a button for it, and the undocumented fallback of walking onto a gate failed silently in three different ways. A dialog opened from inside the tabbed modal shared its z-index and lost to the modal's re-append on every state poll, so the duel stake dialog flashed and vanished. `finishCoop` ran its modal, render and sidebar update unguarded, so a throw anywhere in the sequence stranded the mid-run sidebar on screen for a run that no longer existed. The rest were merely wrong rather than fatal: a duel winner never exits through a gate, so every victory was announced as "YOU DIED" at full HP; non-commit-phase key presses in a duel were dropped in silence, which is why potions looked broken; the gate dialog fired on key press instead of on arrival, greying out the only option that mattered; stake presets were a fixed ladder filtered by affordability, so holding 8 gold offered nothing but "no stake", and it is a capped number field with quick picks now; co-op blocked input for the roughly one second an action took to resolve, so ordinary movement spammed a warning, and own actions may now queue three deep. The day also added armed intent, so opening a run from inside one can be decided up front and fires on arrival at the named gate, with a sidebar banner and a cancel, retiring itself if the target closes or the player leaves.

**Decisions & notes:** Frontend only, deliberately: no engine or settlement behaviour changed, and all 23 parity and convergence vectors still pass. Duels keep the one-action-deep input limit while co-op moves to three, because a duel round is a sealed choice rather than a queued move. The recurring shape here is worth remembering: every one of these bugs sat in the layer the parity suite does not cover (DOM wiring, dialog stacking, page lifecycle, input gating), and the persisted-salt one in particular is a correctness bug that only a reload could expose, so it was invisible to every test that runs a session start to finish in one process.

## 2026-09-15

Player-versus-player duels went in end to end, working through the backend's `docs/PVP_4a_checklist.md` in the order it lays out. The consensus half came first: `combat.ts` gained `playerAttackPlayer` with the section 4 draw order (a miss returns before the dodge roll is drawn, and the draw count is as much consensus as the outcome), `session.ts` gained duel mode as a commit/reveal/apply phase machine with a per-round reseed from both revealed salts, bump-to-attack, death ordering and a winner latch, and `settle.ts` learned the two new entry kinds in all three encodings, with canonical lines now delegating to `canonicalActionBody` so the settle hash and the duel commitment cannot drift apart. Five duel vectors were extracted mechanically from the C++ suite and pinned in `parity_test.ts`, and every pre-existing vector still prints the same hash, so solo and co-op replay is byte-identical to before duels existed. The round then went onto `CoopRunner` as a mode rather than a separate runner, with commit and reveal modelled as action types so they ride the existing ordinal and queue path and the relay never learns duels exist; `duel_test.ts` runs two clients with their own secret salts over a delaying in-memory relay and asserts they converge on the same log, winner, HP and pvp damage. The UI followed: hosting offers "wait here for a duel" with stake presets filtered to what the player can afford, a joiner sees mode and stake before joining (a stake they cannot cover shows as a disabled choice explaining what they hold), the arena shows both HP bars and the round phase, and stepping onto a gate warns twice that it is a forfeit. A version handshake blocks hosting and joining on a rules mismatch, since such a run is rejected only at settlement after the player has played the whole thing, and warns without blocking on a banking mismatch. Then the bug that made all of it moot: `computeClaims` was still the co-op version, so it sent no `duel` field and computed `survived` as "reached a gate", which reports a duel winner (who never exits) as dead and left both characters stuck in an active visit on a confirmed segment that deliberately never times out. It now mirrors the GSP's duel rules, and `tests/e2e/duel.mjs` is the two-browser duel the build order had asked for and nothing had written, which is why this reached a branch at all. The day closed with an adversarial suite: two Node actors holding their own engine copies fight honestly, then take turns trying to steal the result, and every attack is refused. Separately, and from a hand-testing session, the segment cache learned to forget: it only ever grew, so a pruned provisional segment was drawn for the life of the page and, worse, made the gate dialog and the co-op lobby predict chain behaviour from a released coordinate. `coop_play.mjs` joined the e2e scripts as a two-browser driver that clears a whole segment for long sessions the test suites do not reach.

**Decisions & notes:** Three traps are recorded because they each made a test or a check quietly prove nothing. `createMulti` builds sessions with `Object.create`, bypassing class field initialisers, so an unassigned `duelWinner` read as "already decided" and ended every duel early; the settle hashes matching throughout is what narrowed it down. The duel convergence test's first version dawdled 8ms against a 120ms tick, so the fixed tick never fired while the test claimed to cover it, and it now fails if the tick does not fire. Two drafts of the adversarial suite passed for the wrong reasons, once on a forged field the wire format ignores and once because an accepted settlement made every later case vacuous, so each case now asserts the duel is still open before it runs. Also deliberate: the fixed tick runs from the round opening rather than from the opponent acting, because a commit is opaque until it lands and two clients each waiting on the other would wait forever; the salt comes from the platform CSPRNG, not `Math.random`, since unbiasable entropy is the whole point of the round; and the duel mode is read from the visit row rather than local state, because rebuilding a duel's prefix through the co-op engine after an abandonment would reject its commit entries and silently truncate the run. The claim constants mirror `moveprocessor.hpp`, and if they drift every duel is rejected. Verified against a devnet twice, unstaked and staked.

## 2026-09-08

Co-op stopped being something you arrange from the map and became something you walk into, following the backend's move change in spec section 8a: a visit is now local, so you host or join through the gate you are standing at rather than by picking a segment anywhere in the world. `doCoopHost(dir)` and `doCoopJoin(id, dir)` are gate-walks that happen to open or enter a door, and they carry the settlement for the run you are leaving when you are in one, sharing `buildExitSettlement` with the plain gate-walk; the `v` and `j` moves grew a `dir` and an optional settlement to match. Stepping onto a gate whose far side is a confirmed segment now offers three choices instead of silently going through: go alone, join a run already waiting over there, or wait there for a partner, presented by a new `showChoiceModal`. The game modal gained a Co-op tab as the lobby, listing only the runs reachable from where you stand along with the gate to use, and saying why the list is empty when the current segment has no confirmed neighbours. Because a party converges from different sides, each participant now spawns at their own entry gate, read from `entry_directions` on `getvisitinfo`, so `session.ts` was reworked to anchor placement on the gate mouth and fall back to the backend's deterministic ring scan only when two players contest the same tile. The day also covered the state of standing at a segment outside any run, which is exactly where a co-op survivor and a waiting host are left, and added co-op to the in-game help.

**Decisions & notes:** Solo spawn stays byte-identical: the gate mouth is claimed without a wall check, deliberately, so an already-settled run cannot have its spawn moved by the new code, and the ring scan (which draws no RNG) only runs for a later participant who finds the anchor taken. Same-gate and mixed-entry spawn vectors are pinned in the parity tests. Verified with both `npm run coop` Playwright scenarios against the devnet, and the solo flows for discovery, loot, transit, equip and death were re-checked as unaffected.

## 2026-09-05

Co-op Phase 2, the robustness layer from section 11 of the backend's multiplayer spec, landed on the client. The day before, a partner who vanished mid-run left the survivor stuck: settlement needed everyone's consent. Now each client sends checkpoint confirms (`sc` with an action count `n`) every 16 applied actions and as a 30-second heartbeat, starting at n = 0 so a live partner never looks abandoned, with the final confirm carrying the full log length. The co-op sidebar shows the partner's last checkpoint and its age; once it is `ABANDON_WINDOW_BLOCKS` (20) old it offers "continue alone": the shared session is rebuilt at exactly that checkpoint, anything later discarded, the partner is marked absent, and the run plays out solo through the normal keys before settling with `solo_from`. `session.ts` gained the absent state and `markAbsent`, mirroring the C++ engine's turn hand-off when the absent player was mid-turn or last in the round, and the parity tests pin the absent-partner vector. The second commit switched every settlement move (`xc`, the gate-walk settle, the multiplayer `s` and the abandonment `s`) to the GSP's compact proof encoding: `settle.ts` gained an encoder and a mirror decoder for the grammar (numpad move codes, single-letter actions, optional actor prefix for merged logs, maximal runs of identical entries collapsed to `*n`), gated by the `COMPACT_ACTIONS` flag, cutting settlement calldata to roughly a quarter of the JSON array.

**Decisions & notes:** The abandonment path is exercised end to end: `npm run coop` now has a second Playwright scenario where one browser closes mid-run, the window is mined, and the survivor continues alone and settles with the partner banked as a death. `getvisitinfo` confirms are now `{h, n, height}` objects and the settle flow matches on both hash and length. The compact form is pinned against the backend's own parser tests and round-tripped through the decoder for both merged and solo logs; the run-collapsing happens before the GSP sees the log, so the canonical hash lines are unaffected. Remaining co-op work (WebRTC transport, true state channels) moved to the backlog.

## 2026-09-04

Two-player co-op became playable end to end, Phase 1 of the multiplayer plan, in three layers. First the engine: `session.ts` was reworked into a port of the backend's N-participant engine from `SPEC_multiplayer_coop.md`, with participants in canonical order, rounds of one action each followed by a single monster pass, ring spawn, player collision, multi-target monster AI, damage tracking, and shared XP and kill-gold pools. The existing solo surface (`playerX`, `processAction`, and friends) is now a view of participant 0, so nothing else in the app had to change. A new `settle.ts` mirrors the settlement layer: canonical action lines, the `sc` consent hash, pro-rata `splitPool`, `computeClaims` (what the GSP checks a multiplayer settle against), and the wire encoders for the `s` move. Second the network: `net/coop.ts` introduces a pluggable `CoopTransport` (first implementation rides the devnet proxy's relay) and a `CoopRunner` that turns both players' real-time inputs into one merged action log by applying participant i's next action whenever the engine says it is i's turn; each client sends only its own actions, waits are self-authored after a grace window, and the relay history lets a reloaded client rebuild the run. Third the UI in `main.ts`: host, join and leave a lobby from the Map sidebar, a run that starts when the visit turns active with both clients building the same session from on-chain stats, a partner sprite, a co-op sidebar with turn state and projected reward shares, and mutual-consent settlement where participant 0 submits `s` once every other participant's `sc` is on chain. A follow-up gave the host a "Cancel visit" button (the GSP now lets the initiator's `lv` cancel an open visit), taught the validator the GSP's new rule that stat allocation, potion use, equip and discard are refused during any open or active visit, and made the dungeon minimap follow the local participant as "you" with partners in teal rather than always tracking participant 0.

**Decisions & notes:** Solo parity was the constraint the engine port was built around: gold drops go to the shared pool only with more than one participant, so the N = 1 path stays byte-identical to what the chain already replays, and `npm test` now pins the backend's co-op parity vectors (a scripted 2-player run, the settle-hash vector, and the split-pool cases). Log divergence is prevented by construction rather than by reconciliation: an action that is invalid by the time its turn arrives is replaced by a wait on both clients identically, and when everyone is idle nothing happens. This is covered by `coop_test.ts` (two runners over an in-memory relay with random delays and random key presses must converge on the same log, and a late runner must rebuild it from history) plus a two-browser Playwright run, `npm run coop`, that drives confirm, host, join, a shared run, exit and settlement on the devnet. Solo entries and gate-walks are blocked while parked in a co-op visit, mirroring the backend, since it silently drops invalid moves.

## 2026-09-02

One targeted fix for the hosted stack: registration was succeeding on-chain while the UI reported it as rejected. `doRegister` leaned on the pending watcher's two-block budget, but by the time `registerPlayer` had submitted and mined, the recorded start height was already stale and the hosted background miner kept advancing blocks, so the budget lapsed before the frontend ever observed the new player and the client confidently showed a rejection modal for a registration that had worked. The fix waits for the player on a 20-second time budget instead (block budget effectively infinite), never inferring rejection from block count alone, and before reporting failure re-checks authoritatively via a new `Connection.refreshPlayer()`. A genuinely taken name still fails fast, because the proxy rejects the submission outright and the error path catches it.

**Decisions & notes:** Same honesty principle as the 2026-08-28 `waitForMove` work: a lapsed watching budget is evidence of nothing, and the client should only report rejection when it has positively confirmed it.

## 2026-08-28

A protocol-level refactor to follow the GSP dropping segment ids in favour of world coordinates. `player.segment`, `active_visit.segment` and every graph link now carry `{x, y}`, the segment cache is keyed by `"x,y"`, the `ec` move sends `x`/`y`, and `getsegmentinfo` takes two params; the hub is (0, 0). That rippled through the RPC client, connection poll, overworld layout and renderer, the validator, and the whole e2e agent harness. It needs the matching backend commit, since the move format itself changed.

Alongside it, two fixes to how the client reports what happened to a submitted move. `waitFor` had been giving every move a flat five seconds and treating that deadline as proof of rejection, which against three-second blocks plus indexing lag is close to a coin flip and produced confident "the GSP did not apply it" messages for moves that were simply still in flight. The replacement `waitForMove` measures in blocks and separates applied, rejected and pending, so only a genuine rejection is reported as a refusal and a pending move says so while noting the run is intact. Separately, `doGateWalk` was validating before deciding whether to attach a settlement or take a free transit, so the two rules that depend on that decision could only ever fail server-side; it now computes the plan first and validates against it, covering "in a channel with no settlement" (what a lost browser session leaves behind) and "no transit out of a provisional segment". The commit also carries an in-progress account picker that was already sitting in the tree.

**Decisions & notes:** Verified by typecheck, build, and a full self-playing browser agent loop (discover, run, confirm, return to hub) with no anomalies or GSP rejections. The honesty theme is the point of both move-reporting fixes: a timeout is not evidence of rejection, and a client-side validator that runs before the plan exists cannot mirror the backend's rules.

## 2026-07-30

The headline fix was auto-recovering runs that ended server-side without the client noticing. If a dungeon run was force-settled on-chain (the 200-block visit timeout, or a death applied off-client), the state poll used to skip reconciliation whenever it already held a `channelSession`, so the client kept rendering the old dungeon while the map already showed the player back at the hub. The poll now detects that the live run no longer matches the visit the chain reports (not in a channel, or a different visit id) and re-syncs: it starts the knock-back run if the player was pushed back a segment, otherwise it drops to the hub. The reconciliation is guarded by the `busy` flag so it never fires during a gate-walk or settle the client is driving itself. A quick follow-up made the recovery message neutral, since a timeout-driven settle is not a death. The rest of the day was Map-view polish: the world map got a larger inset so it no longer fills the game area, with a "WORLD MAP" title and the legend moved to the bottom to clear the tab bar; the dungeon minimap was wrapped in the same framed panel and titled "DUNGEON MAP" so it is not mistaken for the live playable dungeon; and the World/Dungeon tab switcher got bigger, more visible buttons.

**Decisions & notes:** The auto-recovery path only triggers when the client is idle (`busy` false), so self-driven settles stay authoritative and the reconciliation can only correct genuinely stale state, not race a move in flight.

## 2026-07-29

The day's main work was untangling a soak-bot pathology. The e2e bots had wedged into a permanent two-segment ping-pong (one bot logged over a thousand no-reward transits, roughly 74 wasteful transits per discovery) and the world had frozen at 15 confirmed segments. The root cause was a stall at the d3/d4 boundary: with potions gone and the retreat threshold pinned at 50% HP at depth 4, a healthy inner segment would march outward while the hurt outer one retreated straight back, and the outward-gate fallback just handed back the entry gate. The fix reworked bot routing around a BFS frontier walk over the confirmed segment graph (treating the hub as a traversable node), added anti-backtrack plus an explicit A-B-A-B oscillation detector that forces the bot to grind or park instead of ping-ponging, made hubward retreat monotonic, and relaxed the depth cap (there is no on-chain depth cap; survival is already gated by the depth-aware HP retreat). Grinding a monster to level up fully heals, which breaks the HP stall. After the change, transits-to-discoveries dropped to about 1:1 with zero ping-pong, the frontier climbed from 4 to 6, and bots reached L6-L8 at full health. Two small follow-ups cleaned em-dashes out of the overworld map (the provisional-segment label and the legend now use a middle dot).

**Decisions & notes:** The depth cap was deliberately loosened rather than tightened because the backend enforces no depth limit; letting the HP-retreat heuristic be the only gate keeps the bots honest to what the chain actually allows.

## 2026-07-28

Follow-through on the previous day's push. The most important change was a parity fix in the client-side move validator: `validateGateWalk` had been blanket-rejecting any gate-walk toward an occupied coordinate, but the backend's `HandleGateWalk` now treats walking into a coord-adjacent *confirmed* segment as a free transit (the chain creates the missing link, no discovery and no cooldown). The validator now mirrors that rule exactly, only rejecting when the occupant is another player's provisional segment, so the client never blocks a move the GSP would accept. On the UI side, the game modal became bigger with a fixed size, and the Players tab now surfaces active players first. The e2e bots got two behavioral upgrades: they reuse fixed names so devnet restarts stop cluttering the world with orphan players, and they now engage monsters in a segment before moving on instead of just passing through.

**Decisions & notes:** The validator must track backend rule changes commit-for-commit; the backend silently drops invalid moves, so a stale client validator either blocks legal moves or leaves the user with no feedback on rejected ones.

## 2026-06-28

A big push across two fronts: rounding out overworld/dungeon gameplay and standing up an automated browser-testing stack. On the gameplay side, the overworld was reworked to be coordinate-based with proper gate alignment and entry-gate spawning, and dungeon sessions were switched to use the GSP's effective stats so local play matches the on-chain replay (the core determinism contract). Smaller quality-of-life additions landed too: an inventory and equipment modal with a discard action, persisting the explored map per segment so revisits keep their fog state, auto-selecting same-origin RPC/proxy endpoints when the app is hosted rather than run locally, and sending a transit gate-walk move when leaving a confirmed segment.

The second half of the day built out end-to-end testing from scratch: a headless Playwright harness with a `?e2e` debug hook, then a heuristic self-playing agent that drives the browser as a soak tester, and finally a multi-agent harness where competing players run against a referee. That harness was refactored into a shared `agentcore` and capped off with scripted multiplayer competition tests that assert hard outcomes rather than just smoke-running.

**Decisions & notes:** Dungeon sessions must source stats from the GSP `effective_stats`, never local state, to preserve TS/C++ replay parity. Local rate limiting is off by default, so the test agent needs no throttle flag. The agent cooldown calculation was corrected shortly after the agent landed.
