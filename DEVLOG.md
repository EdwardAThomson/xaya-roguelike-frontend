# Development Log

## 2026-07-30

The headline fix was auto-recovering runs that ended server-side without the client noticing. If a dungeon run was force-settled on-chain (the 200-block visit timeout, or a death applied off-client), the state poll used to skip reconciliation whenever it already held a `channelSession`, so the client kept rendering the old dungeon while the map already showed the player back at the hub. The poll now detects that the live run no longer matches the visit the chain reports (not in a channel, or a different visit id) and re-syncs: it starts the knock-back run if the player was pushed back a segment, otherwise it drops to the hub. The reconciliation is guarded by the `busy` flag so it never fires during a gate-walk or settle the client is driving itself. A quick follow-up made the recovery message neutral, since a timeout-driven settle is not a death. The rest of the day was Map-view polish: the world map got a larger inset so it no longer fills the game area, with a "WORLD MAP" title and the legend moved to the bottom to clear the tab bar; the dungeon minimap was wrapped in the same framed panel and titled "DUNGEON MAP" so it is not mistaken for the live playable dungeon; and the World/Dungeon tab switcher got bigger, more visible buttons.

**Decisions & notes:** The auto-recovery path only triggers when the client is idle (`busy` false), so self-driven settles stay authoritative and the reconciliation can only correct genuinely stale state, not race a move in flight.

## 2026-07-29

The day's main work was untangling a soak-bot pathology. The e2e bots had wedged into a permanent two-segment ping-pong (one bot logged over a thousand no-reward transits, roughly 74 wasteful transits per discovery) and the world had frozen at 15 confirmed segments. The root cause was a stall at the d3/d4 boundary: with potions gone and the retreat threshold pinned at 50% HP at depth 4, a healthy inner segment would march outward while the hurt outer one retreated straight back, and the outward-gate fallback just handed back the entry gate. The fix reworked bot routing around a BFS frontier walk over the confirmed segment graph (treating the hub as a traversable node), added anti-backtrack plus an explicit A-B-A-B oscillation detector that forces the bot to grind or park instead of ping-ponging, made hubward retreat monotonic, and relaxed the depth cap (there is no on-chain depth cap; survival is already gated by the depth-aware HP retreat). Grinding a monster to level up fully heals, which breaks the HP stall. After the change, transits-to-discoveries dropped to about 1:1 with zero ping-pong, the frontier climbed from 4 to 6, and bots reached L6-L8 at full health. Two small follow-ups cleaned em-dashes out of the overworld map (the provisional-segment label and the legend now use a middle dot).

**Decisions & notes:** The depth cap was deliberately loosened rather than tightened because the backend enforces no depth limit; letting the HP-retreat heuristic be the only gate keeps the bots honest to what the chain actually allows.

## 2026-07-28

Follow-through on the previous day's push. The most important change was a parity fix in the client-side move validator: `validateGateWalk` had been blanket-rejecting any gate-walk toward an occupied coordinate, but the backend's `HandleGateWalk` now treats walking into a coord-adjacent *confirmed* segment as a free transit (the chain creates the missing link, no discovery and no cooldown). The validator now mirrors that rule exactly, only rejecting when the occupant is another player's provisional segment, so the client never blocks a move the GSP would accept. On the UI side, the game modal became bigger with a fixed size, and the Players tab now surfaces active players first. The e2e bots got two behavioral upgrades: they reuse fixed names so devnet restarts stop cluttering the world with orphan players, and they now engage monsters in a segment before moving on instead of just passing through.

**Decisions & notes:** The validator must track backend rule changes commit-for-commit; the backend silently drops invalid moves, so a stale client validator either blocks legal moves or leaves the user with no feedback on rejected ones.

## 2026-07-27

A large day split between making the game feel like a real multiplayer app and hardening the self-playing soak bots. The scattered inventory/equipment and help overlays were consolidated into one tabbed game modal (Inventory, Players, Help) with a proper title/start screen wrapping the connect flow. This also fixed a real gameplay gap: potions could not be drunk from the hub at all, and a health potion at full HP was silently wasted; the move layer was already correct, so these were frontend-only fixes. The homepage help was then decoupled from the in-game modal so no game-state machinery is instantiated before a player connects, an M key was added to toggle the world map, and Xaya got a framework credit. Multiplayer presence arrived on the overworld map: every other player is drawn as an initial token on the segment they occupy (from on-chain state, capped at 4 with a +N overflow badge, brighter when in a dungeon). Two bugs fell out of the new UI and were fixed the same day: the map view was trapping movement keys during a dungeon run, and the modal now has a fixed height so switching tabs stops resizing it. On the testing side, the multi-agent referee's gamestate path was fixed and a persistent bot harness added, then the soak bots were taught to actually keep the world alive: push the exploration frontier, retreat when hurt, and only dive shallow so they survive long runs.

**Decisions & notes:** Map tokens are deliberately "honest" presence only; live in-dungeon avatars would need shared or instanced dungeons plus a realtime position relay (channels), which is planned for later. A programmatic connect auto-hides the new start screen, so the `?e2e` hook path is unaffected.

## 2026-06-30

A documentation reconciliation pass brought the state docs back in line with the actual engine. The README and ROADMAP had drifted from the code: they claimed 14 monster types and (inconsistently between the two files) 35 or 28 items, while `monsters.ts` actually defines 12 templates and `items.ts` 31 item definitions. Since the monster and item databases are parity-critical against the C++ backend, stale counts in the docs are worse than cosmetic. The README's project-structure tree was also updated to include modules that had shipped but never been documented: `net/validator.ts` (client-side pre-validation mirroring the backend's move parser), `net/pending.ts` (post-submit revalidation to detect silently-dropped moves), and the `ui/` modal and overlay modules.

**Decisions & notes:** Docs-only change; no engine behavior touched.

## 2026-06-28

A big push across two fronts: rounding out overworld/dungeon gameplay and standing up an automated browser-testing stack. On the gameplay side, the overworld was reworked to be coordinate-based with proper gate alignment and entry-gate spawning, and dungeon sessions were switched to use the GSP's effective stats so local play matches the on-chain replay (the core determinism contract). Smaller quality-of-life additions landed too: an inventory and equipment modal with a discard action, persisting the explored map per segment so revisits keep their fog state, auto-selecting same-origin RPC/proxy endpoints when the app is hosted rather than run locally, and sending a transit gate-walk move when leaving a confirmed segment.

The second half of the day built out end-to-end testing from scratch: a headless Playwright harness with a `?e2e` debug hook, then a heuristic self-playing agent that drives the browser as a soak tester, and finally a multi-agent harness where competing players run against a referee. That harness was refactored into a shared `agentcore` and capped off with scripted multiplayer competition tests that assert hard outcomes rather than just smoke-running.

**Decisions & notes:** Dungeon sessions must source stats from the GSP `effective_stats`, never local state, to preserve TS/C++ replay parity. Local rate limiting is off by default, so the test agent needs no throttle flag. The agent cooldown calculation was corrected shortly after the agent landed.
